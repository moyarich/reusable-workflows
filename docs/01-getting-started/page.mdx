# Getting Started

Reusable workflows are called at the job level.

```yaml
jobs:
  ci:
    uses: moyarich/reusable-workflows/.github/workflows/reusable_node-ci.yml@main
```

Reusable workflows have their own release line. Use `@main` while validating unreleased changes. After the 0.2.0 release is tagged, pin `@v0.2.0` for reproducibility or use the moving `@v0` compatibility alias.

Do not use the npm package release tag for reusable workflow callers. Package tags such as `@moyarich/workspace-tools@0.1.0` identify the installable npm package, not the reusable workflow API.

## Naming contract

Only workflow files prefixed with `reusable_` are part of the supported cross-repository workflow API.

```text
.github/workflows/
├── reusable_node-ci.yml
├── reusable_npm-publish.yml
├── reusable_vscode-extension-publish.yml
└── ci.yml
```

In this example, the first three workflows are public reusable workflows. `ci.yml` is repository-local automation.

## Workflow versioning

Workflow releases are versioned independently from the npm package:

```text
release version
└─ 0.2.0
   ├─ v0.2.0   immutable release tag (after publication)
   └─ v0       moving major alias
```

Workflow release notes are maintained in `CHANGELOG.md`.

## Secrets and permissions

Reusable workflows declare their required inputs, secrets, and permissions through `workflow_call`. The calling repository remains responsible for supplying required secrets and granting compatible permissions.

## Workspace Tools CLI source

Use `workspace-tools-source: registry:npm:0.2.0` for published CLI tooling, `checkout:current` for a caller that is the Workspace Tools repository, or `checkout:upstream;branch:main` to test the upstream checkout. Release and publish commands use named `--package` and `--directory` options.

## Run a workflow with GitHub CLI

`gh workflow run` dispatches a workflow **in the repository specified by `--repo`**. For consumers, dispatch the caller workflow in your own repository; do not try to dispatch a reusable workflow in another repository as a substitute for its caller.

```sh
# Preview package publication from a consumer's .github/workflows/publish.yml
gh workflow run publish.yml --repo OWNER/REPO --ref main \\
  -f package-directory=packages/my-package \\
  -f registry=npm -f dry-run=true

# Find the resulting run, then watch it
gh run list --repo OWNER/REPO --workflow publish.yml --limit 5
gh run watch RUN_ID --repo OWNER/REPO --exit-status
```

Use the actual input names defined under the caller's `on.workflow_dispatch.inputs`. A reusable workflow's `workflow_call` inputs aren't automatically exposed as inputs on the caller. A direct manual run of a workflow in this repository instead uses `--repo moyarich/reusable-workflows` and its own `workflow_dispatch` contract.

## Lucide icons in MDX

The playground provides Lucide React icons through an `Icon` MDX component. Use a [Lucide icon name](https://lucide.dev/icons/) in kebab-case when the icon name comes from content. The generic `Icon` uses Lucide's `DynamicIcon` API. **Tradeoff:** dynamic icons import the icon catalog during build, generate per-icon modules, and may flash while loading. For fixed icons, prefer direct named imports.

```mdx
<Icon name="check-circle" size={20} aria-label="Available" />
<Icon name="terminal" size={20} strokeWidth={1.75} />
```

For static icons in React/MDX pages, import individual icons directly from `lucide-react` to keep builds smaller:

```mdx
import { ArrowRight } from "lucide-react";

<ArrowRight size={18} aria-hidden="true" />
```

Decorative icons should use `aria-hidden="true"`; meaningful icons should have an accessible label.

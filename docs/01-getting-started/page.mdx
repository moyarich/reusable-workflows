# Getting Started

Reusable workflows are called at the job level.

```yaml
jobs:
  ci:
    uses: moyarich/reusable-workflows/.github/workflows/reusable_node-ci.yml@main
```

Reusable workflows have their own release line. Use `@main` while validating unreleased changes. After the 0.2.0 release is tagged, pin `@v0.2.0` for reproducibility or use the moving `@v0` compatibility alias.

Do not use the npm package release tag for reusable workflow callers. Package tags such as `@moyarich/workspace-tools@0.1.0` identify the installable npm package, not the reusable workflow API.

## Naming contract

Only workflow files prefixed with `reusable_` are part of the supported cross-repository workflow API.

```text
.github/workflows/
├── reusable_node-ci.yml
├── reusable_npm-publish.yml
├── reusable_vscode-extension-publish.yml
└── ci.yml
```

In this example, the first three workflows are public reusable workflows. `ci.yml` is repository-local automation.

## Workflow versioning

Workflow releases are versioned independently from the npm package:

```text
release version
└─ 0.2.0
   ├─ v0.2.0   immutable release tag (after publication)
   └─ v0       moving major alias
```

Workflow release notes are maintained in `CHANGELOG.md`.

## Secrets and permissions

Reusable workflows declare their required inputs, secrets, and permissions through `workflow_call`. The calling repository remains responsible for supplying required secrets and granting compatible permissions.

## Workspace Tools CLI source

Use `workspace-tools-source: registry:npm:0.2.0` for published CLI tooling, `checkout:current` for a caller that is the Workspace Tools repository, or `checkout:upstream;branch:main` to test the upstream checkout. Release and publish commands use named `--package` and `--directory` options.
